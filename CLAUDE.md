# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## Status

React 19 + Vite 8 (JavaScript/JSX, no TypeScript). Implements a **Damage Reports** MVP: reports list, create form, and details view with status change. The repo is not yet under git.

## Layout

All code and commands live in the **`project/`** subdirectory, not the repo root. Code is split by **business domain** — Buildings, Assessments, Municipal Approvals — each owning its own data and logic (see *Domain architecture*).

```
project/
  scripts/dev.js                         Spawns API + Vite together (npm start)
  server/
    index.js                             HTTP bootstrap only: create server, dispatch, concat domain route tables
    seed.js                              Fixture data — one slice per domain (seedBuildings / seedAssessments / seedApprovals)
    shared/{http,coerce,paths}.js        send()/readJsonBody(), toBool/toInt/trimStr, GENERATED_DIR
    domains/
      users/                             userStore·usersService·usersRoutes (login/logout/session)
      buildings/                         buildingStore·Rules·Service·Routes, localityReadiness,
                                         occupancyPackageService, mockNotificationServer, notificationClient
      assessments/                       assessmentStore·Service·Routes
      municipalApprovals/                municipalApprovalStore·Service·Routes
      activityLog/                       activityLogStore·Service·Routes (audit of user actions)
      settlementProcesses/               store·service·routes (one record per bulk return-home run)
```

- **UI layer**: Hebrew, RTL (`<html dir="rtl" lang="he">`), full-screen dashboard layout (no centered max-width box — `.app__brand` is a sticky top bar, `.app__main` has the gutters). Palette = light brown + light blue tokens in `src/index.css` (`--brown*`, `--accent*` blue); `src/App.css` uses logical properties (`text-align: start`, `border-inline-start`) for RTL. Enum values shown to users are translated via presentational label maps only (`STATUS_LABELS` in `shared/constants.js`; `ROLE_LABELS` in `App.jsx`; per-screen `STATUS_LABELS` in `SettlementProcesses`/`NotificationCenter`) — the raw values (`STATUS`, `DAMAGE_GRADES`, notification `MODE_OPTIONS` values, `role`) are never changed, and `badge--${status.toLowerCase()}` classes still key off them.
- **Auth**: `POST /login` returns a session `token` + the user (`role`, `settlementId`); the client keeps the token in `localStorage` and `apiClient` attaches it as `X-Auth-Token` on every request. `App.jsx` shows `<Login>` until `GET /session` resolves; a login lasts until `POST /logout`. No signup. Seed users in `server/seed.js`: `sara`(MINISTRY) / `david`(MUNICIPALITY, ירושלים) / `noa`(MUNICIPALITY, תל אביב) / `michal`(APPRAISER), password = `<username>123`. Actions are gated by role **and** settlement scope server-side — see *Domain architecture*.
- **Activity log**: `ReportDetails` shows a "היסטוריית פעולות" section (תאריך ושעה · משתמש · פעולה) fetched from `GET /reports/:id/activity`; it refreshes after an in-screen budget-request and on remount (assessor/authority actions log server-side and appear on next open).
- **Settlement processes** (`server/domains/settlementProcesses/`, `src/domains/settlementProcesses/`): one `SettlementProcess` record (`id, settlementName, startedBy, startedAt, completedAt, status ∈ PROCESSING|COMPLETED`) per bulk return-home run. `ReportsList.handleBulkGenerate` wraps the **unchanged** per-building loop: `POST /settlement-processes` (start, `startedBy` = the session user's `fullName`, `settlementName` = the locality filter or `'כל היישובים'`, `eligibleCount` passed for logging) → run the existing loop → `PATCH /settlement-processes/:id/complete`; an outer try/catch reports an unhandled failure via `POST /settlement-processes/:id/log`. All tracking calls are best-effort (a failure only `console.warn`s, never blocks generation). The **Settlement Processes** screen (route `/settlement-processes`, header nav button) lists them newest-first — five columns only, no logs / IDs / metrics / per-building detail.
- **Technical log** (`server/shared/logger.js`): a dependency-free file logger. Appends one JSON object per line to `server/generated/settlement-process.log` (writes serialised in call order, never throw into the caller). Fields per line as relevant: `timestamp`, `level` (`INFO`/`WARN`/`ERROR`), `event`, **`settlementProcessId`**, `settlementName`, `buildingId`, `notificationAttempt`, `errorMessage` — **no email/body/token/password**. Emitted from: the settlement-process routes (`SETTLEMENT_PROCESS_STARTED` / `SETTLEMENT_ELIGIBLE_BUILDINGS_FOUND` with `buildingCount` / `SETTLEMENT_PROCESS_COMPLETED` / `SETTLEMENT_PROCESS_FAILED`), the `POST /buildings/:id/return-home-package` route (`BUILDING_HANDLING_STARTED`/`_COMPLETED`), `occupancyPackageService` (`PDF_GENERATION_STARTED`/`_COMPLETED`, `NOTIFICATION_SEND_STARTED`) and `notificationClient` (`NOTIFICATION_ATTEMPT_FAILED` WARN, `NOTIFICATION_RETRY_STARTED`, `NOTIFICATION_SEND_SUCCEEDED`). These are pure log lines — the PDF flow, retry, idempotency and notification server are behaviourally unchanged; the retry loop still breaks only on `SENT`. `generateReturnHomePackage` passes `settlementId` in the notification payload for log context (the mock server ignores it).
- **System Health** (`server/domains/systemHealth/`, `src/domains/systemHealth/`, route `/system-health`, header nav button): read-only. `systemHealthService.getSnapshot()` composes from existing data — `settlementProcessService.list()` and `mockNotificationServer.listNotifications()` — and returns `{ settlementProcesses:{completed, processing}, notifications:{successful, failed, retryCount}, performance:{averageSettlementDurationMs} }`. `retryCount` = notification records − distinct `idempotencyKey`s (extra attempts). `averageSettlementDurationMs` = mean `completedAt − startedAt` over completed processes. The screen renders three `.locality-summary` stat-tile groups; duration shown as `Ns`. No charts/alerts/external monitoring; nothing is mutated.
- **Log correlation** (`server/shared/logContext.js`): an `AsyncLocalStorage` holds the `settlementProcessId` for the current async chain; `logger` stamps it onto every record automatically. The client sends the `SettlementProcess.id` (its existing uuid — nothing added to the entity) as `X-Settlement-Process-Id` on each `POST /buildings/:id/return-home-package`; the route runs its body inside `runWithProcessId(id, …)`, and the settlement-process routes wrap their `logger.*` calls the same way. So every line for one run — including PDF, notification, retry and completion — shares the id, and concurrent runs stay separable. One-off single-building generations send no header → no `settlementProcessId`. No signatures on the PDF/retry/notification code changed.

## Architecture

- **Domain architecture** (server): each domain has a **private store** (`const store = new Map()` / array, never exported), a **service** = its public API, and a **routes** table. No domain reads or writes another domain's store.
  - `users/usersService` — `login(username,password)` → `{token,user}` (user carries `role`), `logout(token)`, `userForRequest(req)` (reads `X-Auth-Token`), **`authorize(req, action)`** → `{ok, user}` or `{ok:false, status:401|403, error}`. Private `sessions` Map. Routes: `POST /login`, `POST /logout`, `GET /session`.
  - `users/permissions.js` — `can(role, action)` (role→action policy) **and** `inSettlementScope(user, buildingSettlementId)` (area of responsibility). Role matrix: **MINISTRY** = all three business actions; **MUNICIPALITY** = `DECIDE_MUNICIPAL_APPROVAL` only; **APPRAISER** = `UPDATE_ASSESSMENT` only. `inSettlementScope` = `true` unless the user is `MUNICIPALITY` with a different `settlementId` (MINISTRY / APPRAISER / no-token are never scoped). Seed users: `sara`=MINISTRY, `david`=MUNICIPALITY/ירושלים, `noa`=MUNICIPALITY/תל אביב, `michal`=APPRAISER.
  - **User** carries `role` + `settlementId` (null for non-MUNICIPALITY). **Building** carries `settlementId` (seed = its locality; on POST, `body.settlementId` or `localityOf(address)`).
  - **Enforcement** (server-authoritative):
    - Business actions — the route loads the building (`getRawBuilding` → 404 if missing), then `usersService.authorize(req, ACTION, building.settlementId)` **first**. On failure: 401/403 with a Hebrew message, **no data change, no activity record**. Gated: `PATCH .../assessment`, `PATCH .../authority-approval`, `POST .../budget-request`.
    - Reads — `GET /reports` filters out buildings outside the caller's scope; `GET /reports/:id` and `GET /reports/:id/activity` return **403** for an out-of-scope building. `PATCH .../status`, return-home-package and notifications stay ungated.
  - Client mirrors the policy in `src/domains/users/permissions.js` (`roleCanViewAssessorPortal` etc.) — hides portal nav buttons, blocks `/assessor` & `/authority` routes with `<AccessDenied>`, disables "פתח בקשת תקציב". The list already arrives scoped from the server; UI is convenience only.
  - `activityLog/activityLogService` — `recordFromRequest(req, {action, entityType, entityId})` (resolves the actor via `usersService`, appends a `{id,userId,userName,action,entityType,entityId,timestamp}` record — never mutates existing ones) and `listForBuilding(id)`. Route: `GET /reports/:id/activity` (newest first). Logged actions: `PATCH .../assessment` → `עדכון שמאות`, `PATCH .../authority-approval` → `אישור מבנה`/`דחיית מבנה` (per `approved`), `POST .../budget-request` → `פתיחת בקשת תקציב` (only on the false→true transition; `openBudgetRequest` returns `opened`).
  - `assessments/assessmentService` — `getAssessment(buildingId)` / `saveAssessment(buildingId, input)` (owns `DAMAGE_GRADES` + validation).
  - `municipalApprovals/municipalApprovalService` — `getApproval(buildingId)` / `saveApproval(buildingId, input)`.
  - `buildings/buildingService` — owns building core + rehab process + the national-dashboard readiness calc. `listBuildings()` / `getBuilding(id)` **compose** the response: building fields **plus** `assessment` (from `assessmentService.getAssessment`) **plus** `authorityApproval` (from `municipalApprovalService.getApproval`) **plus** `readyForLocalityOpening` (from `localityReadiness`, fed those two). So `GET /reports*` and every mutating endpoint return the same wire shape as before — the two sub-objects are just no longer stored *on* the building.
  - The `assessment` / `authority-approval` PATCH routes live in their own domain, write only their store, then call `buildingService.getBuilding(id)` to shape the (composed) response. `index.js` does `[...buildingRoutes, ...assessmentRoutes, ...municipalApprovalRoutes]`; patterns are anchored so order doesn't matter. A **string** `body` is sent raw with the given headers (file serving); anything else is JSON. All data is in-memory — **resets on restart**.
- **Endpoints**: `POST /login`, `POST /logout`, `GET /session`; `GET/POST /reports`, `GET /reports/:id`, `GET /reports/:id/activity`, `PATCH /reports/:id/status`, `PATCH /reports/:id/assessment`, `PATCH /reports/:id/authority-approval`, `POST /reports/:id/budget-request`, `POST /buildings/:id/return-home-package`, `GET /files/:name`, `POST /notifications/send`, `GET/POST /notifications/mode`, `GET /notifications`, `GET/POST /settlement-processes`, `PATCH /settlement-processes/:id/complete`, `POST /settlement-processes/:id/log`, `GET /system-health`.
- **Business rules are centralized per domain**: `src/domains/buildings/buildingRules.js` (client) and `server/domains/buildings/buildingRules.js` (server) hold `isRehabReady`, `needsSocialApproval`, `canOpenBudgetRequest`, `hasBudgetRequest`, `isQueuedForWork`, `localityOf`, `STATUS_FLOW`/`nextStatus`. Compose these; do **not** re-inline the conditions.
- **Status flow**: `STATUS_FLOW = ['WAITING_FOR_VALIDATION', 'NEW', 'IN_REVIEW', 'REHAB_IN_PROGRESS', 'REHAB_DONE']`, defined in `server/domains/buildings/buildingRules.js` and `src/shared/constants.js` — keep the two in sync. New reports start at `WAITING_FOR_VALIDATION`. Forward-only: advance to the next status or stay put; other transitions → **409**, unknown status → **400**. The details dropdown offers `current` + `nextStatus(current)`. The two `REHAB_*` labels in `STATUS_LABELS` are Hebrew.
- **DamageReport fields**: `reporterName`, `address`, `damageType`, `description` (required on POST), `status`, `createdAt`, plus booleans `hasDamagePhotos` / `hasEngineerReport` / `eligibilityChecked` / `socialApproval` / `budgetRequestOpened` (default `false`) and `apartmentsInBuilding` (int ≥ 0, default `0`). The create form collects the first four booleans + apartment count; `budgetRequestOpened` is set only via `POST /reports/:id/budget-request` (guarded by `canOpenBudgetRequest`, idempotent). POST normalizes everything through `toBool` / `toApartmentCount`.
- **Details-screen gates** (`ReportDetails.jsx`): `isRehabReady` drives the "ניתן להתחיל שיקום" banner. **"פתח בקשת תקציב"** calls `POST /reports/:id/budget-request`, enabled only when `canOpenBudgetRequest(report) && !budgetRequestOpened`.
- **Occupancy Package Service** ("שרות תיק אכלוס"), part of the Buildings domain: `src/domains/buildings/occupancyPackageService.js` + `server/domains/buildings/occupancyPackageService.js`. `canGenerateReturnHomePackage` = `isQueuedForWork && hasBudgetRequest && status === 'REHAB_DONE'`. `POST /buildings/:id/return-home-package` waits 1 s (simulated work), writes a formal Hebrew **RTL HTML** document (building id, address, apartments, eligibility/budget/rehab status, "ניתן לאכלוס מחדש") to `server/generated/`, returns `{ url, fileName }`. `GET /files/:name` serves it (`?download=1` → `Content-Disposition: attachment`). *A true binary PDF was skipped* — Hebrew glyphs need an embedded font + PDF lib; the HTML doc is print-to-PDF ready. The list shows a per-row **"הפק תיק אכלוס מחדש"** button (`ReturnHomePackageButton.jsx`) with view/download links when eligible.
- **Portals pattern** (`src/domains/assessments/AssessorPortal.jsx` → `/assessor`, `src/domains/municipalApprovals/LocalAuthorityPortal.jsx` → `/authority`), each reached from a header button in `ReportsList`. Same shape: a building table (address, `localityOf`, status badge, "…קיים/ה") → click a row → **modal** (`.modal-overlay` + `.modal--form`) form → `PATCH` → the value is stored in that domain's own store and **composed onto** the `GET /reports*` response, shown read-only in a section on `ReportDetails`. Survives page refresh (in-memory, resets on restart); decision-making rules untouched.
  - **Assessor** → `report.assessment` via `PATCH /reports/:id/assessment` (Assessments domain) — `damageGrade` (`קל`/`בינוני`/`חמור`, validated), `notes`, `inspectionDate` (required), `reinspectionRequired`. Section: "הערכת שמאי".
  - **Local authority** → `report.authorityApproval` via `PATCH /reports/:id/authority-approval` (Municipal Approvals domain) — `waterOk` / `electricityOk` / `accessRoadsOpen` / `hazardsCleared` / `approved` booleans + `notes` (all `toBool`-coerced, no hard validation). Section: "אישור רשות מקומית".
- **List-screen columns/filters** (`ReportsList.jsx`): "ממתין בתור לעבודה" = `isQueuedForWork`; "מוכן לשחרור תקציב" = `isRehabReady`; "תיק אכלוס מחדש" column = `ReturnHomePackageButton` when `canGenerateReturnHomePackage` (or a bulk-generated URL exists). A **locality `<select>`** (values = `localityOf(address)` = text after the last comma) plus two independent filter checkboxes; all AND together into `visibleReports`.
- **Locality-opening readiness**: computed **server-side** in `server/domains/buildings/localityReadiness.js` (`readyForLocalityOpening(building, assessment, approval)` — the assessment & approval are handed in by `buildingService.compose`, obtained via the two domain APIs) and delivered as `report.readyForLocalityOpening`. Client `isReadyForLocalityOpening(report)` just reads that field; `LocalitySummary` still buckets not-ready buildings via `hasAssessorAssessment` / `hasLocalAuthorityApproval` (which read the composed `assessment` / `authorityApproval`). Conditions: all rehab (`isRehabReady` + `!needsSocialApproval` + `hasBudgetRequest`) + `returnHomePackageGeneratedAt` (stamped by the `POST /buildings/:id/return-home-package` route) + assessment exists + grade `קל`/`בינוני` + `authorityApproval.approved`. A "כשיר לפתיחת יישוב" כן/לא column shows it per row. When a locality is picked in the existing filter, `LocalitySummary` renders a card over `reports.filter(localityOf === locality)` (not narrowed by the checkboxes) with: total, ready, not-ready, and a **priority partition** of the not-ready set — waiting-for-assessor (`!assessment`) → waiting-for-authority (`assessment && !approved`) → other-reasons (`assessment && approved`), so the three sum to not-ready. All values are derived from `reports` state, so they recompute on any data change; `ReportsList` refetches (`refreshReports`) after bulk generation and after an individual `ReturnHomePackageButton` fires (`onGenerated`), and remounts→refetches when you return from the portals/details. Seed: the 8 lowest-index `ירושלים` buildings carry varied `assessment`/`authorityApproval`/`returnHomePackageGeneratedAt` so every summary bucket is non-zero (5 ready).
- **Bulk return-home packages** (`ReportsList.jsx`, no new endpoint/mechanism): one button whose label is "הפק תיקי איכלוס לכל היישוב" when a locality is picked, else "הפק תיקי אכלוס לכל המבנים הזכאים". `handleBulkGenerate` loops `visibleReports.filter(canGenerateReturnHomePackage)` **sequentially**, calling the existing `generateReturnHomePackage(id)` (the single-building API) per building, collecting `{ [id]: url }` into `bulkUrls`. A modal shows a spinner + "מפיק תיקים..." while running, then "ההפקה הושלמה" / "הופקו X תיקי חזרה לבית". `bulkUrls[id]` is passed to `ReturnHomePackageButton` as `documentUrl`, which then renders a 📄 link to the saved document. ~1 s/building (server-simulated), so 10 ≈ 10 s.
- **Seed data** (`server/seed.js`): the 4 named buildings plus 20 generated `ירושלים` buildings — first 10 eligible for a return-home package, last 10 in `IN_REVIEW` without a budget request. Every building has a valid `familyEmail`. Seed assessments / approvals for the enriched `ירושלים` buildings go into `seedAssessments` / `seedApprovals` (each store loads only its slice).
- **Mock Notification Server** (`server/domains/buildings/mockNotificationServer.js`): stands in for a flaky external messaging system — one call per request, no retries, `sendNotification` never throws (so package generation is unaffected). Has a **mode** (`NOTIFICATION_MODES`): `SUCCESS` (all SENT), `ALWAYS_FAIL` (all FAILED), `FAIL_FIRST` (first attempt per `buildingId` FAILED, every later attempt for that id SENT; the attempted-`Set` persists for the whole server run — across mode changes — reset only by restart), `RANDOM` (independent `Math.random() < 0.3` roll per call), `RESPONSE_LOST` (message really is sent — record logged as `SENT` — but `sendNotification` returns `{status:'NO_RESPONSE'}` instead of an ack, so the retry wrapper keeps trying, producing 3 `SENT` records). `sendNotification({buildingId, email, subject, body})` → `{status:'SENT'|'FAILED', messageId}`. **Every** call — success or failure — pushes one record to the in-memory log and appends a CSV row to `server/generated/notifications.csv` (`messageId,buildingId,email,subject,date,time,status`, quoted). Endpoints: `POST /notifications/send`, `GET/POST /notifications/mode` (`{mode}`), `GET /notifications` (log, newest first, no `body`).
- **Retry policy** (`server/domains/buildings/notificationClient.js`): `sendNotificationWithRetry(payload)` calls the mock server up to **3 times**, immediately (no delay), stopping at the first `SENT`; returns the last attempt's result. The mock server logs **every** attempt as its own record — retries never mutate existing records. Both `generateReturnHomePackage` and the `POST /notifications/send` route go through this wrapper; the mock server module itself is unchanged.
- **Idempotency** (in `sendNotification`): each send carries an `idempotencyKey` — for the MVP it defaults to `buildingId` (so all retries for one building share it; `POST /notifications/send` also accepts an explicit `idempotencyKey`). Before sending, if the log already holds a `SENT` record with that key, it returns `{status:'ALREADY_SENT', messageId:<original>}` — **no send, no new record**. This is what stops `RESPONSE_LOST` (and plain re-generation) from notifying a family twice: attempt 1 logs `SENT`, attempts 2–3 short-circuit to `ALREADY_SENT`. `FAILED` records don't count, so `ALWAYS_FAIL` still produces 3 attempts. The retry wrapper is untouched (it just doesn't see `SENT`, so it runs all 3 no-op iterations). Records now include `idempotencyKey`; the Notification Center shows it as a column.
- **Family notification on package generation**: `generateReturnHomePackage` (`server/domains/buildings/occupancyPackageService.js`), *after* the document is written, calls `sendNotificationWithRetry` once — subject `אישור חזרה לבית <address>`, fixed Hebrew body. So both the single-building button and the bulk action notify (with retry) automatically; no separate trigger. The `POST /buildings/:id/return-home-package` response carries the final attempt's `messageId`. The package is still produced even if all 3 notification attempts fail.
- **Notification Center screen** (`NotificationCenter.jsx`, hash route `/notifications`): a mode `<select>` (`.notif-mode`) bound to `GET/POST /notifications/mode`, plus a table of all attempts (Message ID, Building ID, address — joined from `/reports` by `buildingId` — email, Subject, Date & Time, Status badge `badge--sent` / `badge--failed`). Reached via the "מרכז הודעות" button in the list-screen header (`onOpenNotifications` prop from `App.jsx`).
- **DamageReport `familyEmail`**: `string`, collected by the create form (`type="email"`, required), normalized on POST. Not in `REQUIRED_FIELDS` (API stays lenient; default `''`).
- **Frontend → API**: the browser calls `/api/*`; Vite's dev proxy (`vite.config.js`) strips `/api` and forwards to `localhost:4000`. In a production build there is no proxy — you would need to serve the API and rewrite, or point `BASE_URL` in `src/shared/apiClient.js` at the real host.
- **Routing**: no router library. `useHashRoute` in `App.jsx` reads `window.location.hash`; `navigate()` sets it. `ReportDetails` is keyed by report id so it remounts (and refetches) on navigation.
- **Data fetching**: each view fetches in a `useEffect` with an `active` flag for cleanup. No shared cache — returning to the list refetches, which is how a newly created report appears.

## Commands

Run from `project/`:

- `npm start` — API + Vite dev server together (use this for the full app)
- `npm run dev` — Vite only
- `npm run server` — API only
- `npm run build` — production build to `project/dist/`
- `npm run lint` — **oxlint** (not ESLint)

There is **no test runner configured**. If adding tests, wire up Vitest.

## Linting

Lint config is `project/.oxlintrc.json` with the `react` and `oxc` plugins. `react/rules-of-hooks` is an error; `react/only-export-components` is a warning (constant exports allowed) — keep non-component exports out of `.jsx` component files or expect a warning.

## Notes

- React 19 with `StrictMode`; entry point is `src/main.jsx` mounting `<App />` into `#root` (`index.html`). StrictMode double-invokes effects in dev, so GET requests fire twice locally — harmless.
- Styling: hand-written CSS with design tokens (`:root` vars) in `src/index.css`; component styles in `src/App.css`. No CSS framework. Leftover template assets in `src/assets/` and `public/` are unused.


## Project Context & Guidelines

- **Tech Stack:** React 19, Vite 8, and JavaScript/JSX (no TypeScript).
