# מערכת ניהול שיקום מבנים — משרד הבינוי והשיכון

מערכת ניהול מקצה‑לקצה לניהול תהליך השיקום של מבנים שנפגעו, מרגע פתיחת הדיווח ועד לאישור חזרת התושבים לבתיהם ופתיחת היישוב מחדש. המערכת מאגדת תחת קורת גג אחת את משרד השיכון, השמאים החיצוניים והרשויות המקומיות, עם חלוקת אחריות ברורה, הרשאות לפי תפקיד ותחום אחריות, תיעוד מלא של פעולות המשתמשים, לוגים טכניים ומסך בריאות מערכת.

> **סטטוס:** MVP מלא ועובד מקצה‑לקצה. כל הנתונים בזיכרון (in‑memory) ומתאפסים בהפעלה מחדש של השרת.

## סקירה כללית

התהליך העסקי שהמערכת מנהלת:

1. **דיווח נזק** נפתח עבור מבנה, עם נתוני רקע (כתובת, סוג נזק, מספר דירות, אימייל למשפחה).
2. המבנה עובר **תהליך שיקום** מדורג: `ממתין לאימות → חדש → בבדיקה → מבנה בתהליך שיקום → תהליך שיקום הסתיים`.
3. לאורך הדרך נאספים תנאי זכאות: קיימות תמונות נזק, קיים דו"ח מהנדס, בוצעה בדיקת זכאות, ובמידת הצורך — **אישור חברתי** (למבנים עם יותר מ‑24 דירות).
4. כאשר המבנה כשיר — נפתחת **בקשת תקציב**, ולאחר סיום השיקום מופק **תיק אכלוס מחדש** (מסמך רשמי) ונשלחת הודעת אישור למשפחה.
5. במקביל, **שמאי חיצוני** מזין הערכת נזק, ו**הרשות המקומית** מאשרת שהתשתיות והסביבה בטוחות.
6. **לוח הבקרה הארצי** מציג לכל יישוב תמונת מצב מרוכזת: כמה מבנים כשירים לפתיחת היישוב וכמה עדיין לא — ומדוע.
7. מנהל מחוז מפעיל **הפקה מרוכזת** של תיקי האכלוס לכל היישוב בפעולה אחת, כאשר כל הפעלה נרשמת ומתועדת.

## יכולות המערכת

### ניהול מבנים ותהליך שיקום
- רשימת מבנים עם סינון לפי יישוב, לפי "ממתין בתור לעבודה" ולפי "מוכן לשחרור תקציב".
- יצירת דיווח חדש, מסך פרטי מבנה, ושינוי סטטוס בתהליך מדורג (קדימה בלבד; מעברים לא חוקיים נחסמים).
- חיווי "ניתן להתחיל שיקום" לפי תנאי הזכאות.
- **פתיחת בקשת תקציב** — מותרת רק כשכל תנאי הזכאות מתקיימים; רגולציית אישור חברתי נאכפת עבור מבנים גדולים.

### הפקת תיקי אכלוס מחדש
- הפקת מסמך רשמי בעברית (RTL) עבור מבנה בודד — מזהה מבנה, כתובת, מספר דירות, סטטוס זכאות/תקציב/שיקום והמשפט "ניתן לאכלוס מחדש". צפייה והורדה.
- **הפקה מרוכזת** לכל היישוב (או לכל המבנים הזכאים) — לולאה סדרתית מעל המנגנון הקיים, עם מודל טעינה וסיכום "הופקו X תיקי חזרה לבית".

### שליחת הודעות למשפחות
- **שרת הודעות מדומה** עם מצבי הפעלה נבחרים: `הצלחה`, `כשל תמידי`, `כשל בניסיון הראשון`, `כשל אקראי (~30%)`, `אובדן תשובה (Timeout)`.
- **מנגנון ניסיונות חוזרים** — עד 3 ניסיונות מיידיים, עצירה בהצלחה הראשונה.
- **Idempotency** — מפתח ייחודיות לכל מבנה מבטיח שכל משפחה מקבלת הודעת אישור **פעם אחת בלבד**, גם תחת ריטריי ואובדן תשובה.
- **מרכז הודעות** — יומן מלא של כל ניסיון שליחה (מזהה, מבנה, כתובת, נושא, תאריך/שעה, סטטוס) + קובץ CSV.

### פורטל שמאים
- מסך ייעודי לבחירת מבנה והזנת הערכת נזק: דרגת נזק (קל / בינוני / חמור), הערות, תאריך בדיקה, האם נדרשת בדיקה חוזרת.
- ההערכה מוצגת באזור "הערכת שמאי" במסך פרטי המבנה.

### פורטל רשויות מקומיות
- מסך ייעודי לעדכון מצב תשתיות וסביבה: אספקת מים/חשמל תקינה, דרכי גישה פתוחות, מפגעים סביבתיים פונו, והחלטת אישור/דחייה + הערות.
- הנתונים מוצגים באזור "אישור רשות מקומית" במסך פרטי המבנה.

### לוח הבקרה הארצי
- עמודה "כשיר לפתיחת יישוב" (כן/לא) לכל מבנה, מחושבת בשרת מכלל תנאי השיקום + הפקת תיק החזרה + הערכת שמאי בדרגה קלה/בינונית + אישור רשות מקומית.
- **כרטיס סיכום יישוב** לאחר בחירת יישוב בסינון: סה"כ מבנים, כשירים, אינם כשירים, וחלוקה של הלא‑כשירים לפי "החוסם הבא" — ממתינים להערכת שמאי / ממתינים לאישור רשות / מסיבות אחרות.

### משתמשים, הרשאות ותיעוד
- **התחברות/התנתקות** מבוססת token בזיכרון (ללא JWT, ללא הרשמה). המשתמש נשאר מחובר עד להתנתקות.
- **תפקידים:** `MINISTRY`, `MUNICIPALITY`, `APPRAISER` — כל פעולה עסקית נבדקת בשרת לפי תפקיד המשתמש.
- **תחום אחריות:** משתמשי רשות מקומית מוגבלים ל‑`settlementId` שלהם — רואים ומעדכנים רק מבנים ביישובם; גישה ישירה למבנה מיישוב אחר מוחזרת ב‑403.
- **יומן פעולות** — כל עדכון שמאות / אישור‑דחיית רשות / פתיחת בקשת תקציב יוצר רשומת תיעוד (משתמש, פעולה, תאריך). מוצג באזור "היסטוריית פעולות" במסך המבנה. רשומה נוצרת רק כאשר הפעולה בוצעה בהצלחה.

### תהליכי יישוב, לוגים ובריאות המערכת
- **מסך "תהליכי יישוב"** — רשומת `SettlementProcess` לכל הפעלה של הפקה מרוכזת (`PROCESSING` → `COMPLETED`), עם שם היישוב, מי הפעיל, וזמני התחלה/סיום.
- **לוג טכני** — קובץ `settlement-process.log` (שורת JSON לכל אירוע): תחילת/סיום תהליך, מספר מבנים כשירים, ולכל מבנה — תחילת/סיום הפקת PDF, שליחת הודעה, כישלון ניסיון, ריטריי, הצלחה, סיום. רמות `INFO` / `WARN` / `ERROR`. ללא מידע רגיש.
- **מזהה קורלציה** — כל שורות הלוג של אותה הפעלת יישוב נושאות את אותו `settlementProcessId`, כך שניתן לעקוב אחר ריצה שלמה גם כשריצות מקבילות משתלבות בקובץ.
- **מסך "בריאות המערכת"** — מדדים מחושבים: תהליכי יישוב (הושלמו / בתהליך), הודעות (נשלחו בהצלחה / נכשלו / מספר ניסיונות חוזרים), וביצועים (משך תהליך יישוב ממוצע).

### עיצוב
- ממשק עברי מלא עם תמיכת RTL, פריסת דשבורד במסך מלא, ופלטת צבעים מודרנית (חום בהיר + כחול בהיר).

## ארכיטקטורה

המערכת בנויה כ**מונוליט מחולק לפי תחומי אחריות (domains)**. כל תחום מחזיק את הנתונים והלוגיקה שלו בלבד, חושף **שירות (service) כ‑API פנימי**, ומתקשר עם תחומים אחרים דרך אותם שירותים — לעולם לא בגישה ישירה ל‑store של תחום אחר.

```
┌──────────────────────────  Frontend (React + Vite, hash router)  ──────────────────────────┐
│  domains/{buildings, assessments, municipalApprovals, users, settlementProcesses,          │
│           systemHealth}  +  shared/{apiClient, constants, StatusBadge}                      │
└───────────────────────────────────────────┬───────────────────────────────────────────────┘
                                            │  fetch  /api/*   (Vite dev-proxy → :4000)
┌───────────────────────────────────────────▼───────────────────────────────────────────────┐
│  Backend  (node:http, אפס תלויות, in-memory)                                                │
│                                                                                           │
│   index.js  ── מרכיב את טבלאות ה-routes של כל התחומים ומנתב                                  │
│                                                                                           │
│   domains/                                                                                 │
│     users/               store · service (login/logout/authorize) · routes · permissions   │
│     buildings/           store · rules · service · routes · localityReadiness               │
│                          occupancyPackageService · notificationClient · mockNotificationServer │
│     assessments/         store · service · routes                                          │
│     municipalApprovals/  store · service · routes                                          │
│     activityLog/         store · service · routes                                          │
│     settlementProcesses/ store · service · routes                                          │
│     systemHealth/        service · routes  (קורא נתונים מהתחומים האחרים, לא משנה דבר)         │
│                                                                                           │
│   shared/  http · coerce · paths · logger · logContext (AsyncLocalStorage)                 │
│   seed.js  ── נתוני דמו, פרוסה אחת לכל תחום                                                  │
└───────────────────────────────────────────────────────────────────────────────────────────┘
```

**עקרונות מנחים:**

- **בעלות על נתונים (ownership):** רק שירות השמאויות כותב הערכות; רק שירות הרשויות כותב אישורים; שירות המבנים מרכיב את התגובה עם נתונים מהתחומים האחרים דרך ה‑APIs שלהם, כך שפורמט התגובה כלפי הלקוח נשמר זהה.
- **גבולות ברורים:** ה‑store של כל תחום פרטי (`const store = new Map()` — לא מיוצא). שכבת ה‑routes היא נקודת ההרכבה שרשאית לגעת בכמה תחומים.
- **אכיפה בצד השרת:** כל בדיקות ההרשאה, תפקיד ותחום אחריות מתבצעות בשרת. ה‑UI מסתיר/משבית פעולות שאינן מותרות — אך אינו מקור האמת.
- **התנהגות עסקית משומרת:** מנגנון הריטריי, ה‑Idempotency, שרת ההודעות המדומה ותהליך הפקת המסמך לא שונו לאורך הפיתוח — יכולות חדשות עוטפות אותם ולא נוגעות בהם.

## תהליך הדגל: הפקת תיקי אכלוס ליישוב

לחיצה על **"הפק תיקי אכלוס לכל היישוב"** מפעילה את הרצף הבא — עוטף את מנגנון ההפקה הקיים מבלי לשנותו:

```
לקוח  ─POST /settlement-processes {settlementName, eligibleCount}──▶  נוצרת רשומת SettlementProcess (PROCESSING)
       (השרת רושם ללוג: SETTLEMENT_PROCESS_STARTED, SETTLEMENT_ELIGIBLE_BUILDINGS_FOUND)

  לכל מבנה כשיר בתצוגה (סדרתית):
  לקוח ─POST /buildings/:id/return-home-package  (עם כותרת X-Settlement-Process-Id)──▶  שרת
       השרת מריץ את הבקשה בתוך AsyncLocalStorage עם מזהה התהליך, ורושם ללוג:
         BUILDING_HANDLING_STARTED
         PDF_GENERATION_STARTED → (המתנה מדומה של שנייה, כתיבת המסמך) → PDF_GENERATION_COMPLETED
         NOTIFICATION_SEND_STARTED
           → עד 3 ניסיונות:  NOTIFICATION_ATTEMPT_FAILED (WARN) / NOTIFICATION_RETRY_STARTED / NOTIFICATION_SEND_SUCCEEDED
         BUILDING_HANDLING_COMPLETED
       שליחת ההודעה עוברת דרך Idempotency — משפחה שכבר קיבלה אישור לא תקבל שוב.

לקוח  ─PATCH /settlement-processes/:id/complete──▶  הרשומה עוברת ל-COMPLETED, completedAt מתעדכן
       (השרת רושם ללוג: SETTLEMENT_PROCESS_COMPLETED)

בכשל בלתי מטופל:  לקוח ─POST /settlement-processes/:id/log──▶  נרשם ERROR: SETTLEMENT_PROCESS_FAILED
```

לאיתור כל הלוגים של הפעלה מסוימת — הביאו את מזהה הרשומה ממסך "תהליכי יישוב" וסננו את הקובץ:

```bash
grep '"settlementProcessId":"<id>"' server/generated/settlement-process.log
# או, מעוצב:
jq -c 'select(.settlementProcessId=="<id>")' server/generated/settlement-process.log
```

## מודל ההרשאות

| פעולה | MINISTRY (משרד השיכון) | MUNICIPALITY (רשות מקומית) | APPRAISER (שמאי) |
|---|:---:|:---:|:---:|
| צפייה במבנים | ✅ כל המבנים | ✅ ביישוב שלו בלבד | ✅ כל המבנים |
| עדכון הערכת שמאי | ✅ | ⛔ | ✅ |
| אישור / דחיית רשות מקומית | ✅ | ✅ (ביישוב שלו) | ⛔ |
| פתיחת בקשת תקציב | ✅ | ⛔ | ⛔ |

- **תחום אחריות:** משתמש `MUNICIPALITY` מקושר ל‑`settlementId`. רשימת המבנים מגיעה מסוננת מהשרת, וכל ניסיון גישה או פעולה על מבנה מחוץ ליישובו מוחזר ב‑`403` — ללא החזרת נתונים וללא רשומת תיעוד.
- הבדיקות מתבצעות בשרת **לפני** כל פעולה עסקית. ה‑UI מסתיר כפתורי ניווט ופעולות לפי התפקיד, אך השרת הוא מקור האמת.
- אין JWT, אין Claims, אין ספריות הרשאות חיצוניות — token פשוט ב‑Map בזיכרון (`X-Auth-Token`).

## טכנולוגיות

| שכבה | טכנולוגיה |
|---|---|
| Frontend | React 19, Vite 8, JavaScript/JSX (ללא TypeScript), ניתוב hash עצמאי (ללא ספריית router) |
| Backend | `node:http` בלבד — **אפס תלויות ריצה בשרת** |

| לוגים | logger עצמאי מבוסס קבצים (JSON‑lines) + `AsyncLocalStorage` לקורלציה |
| Lint | oxlint (`react`, `oxc`) |
| הרצה | `scripts/dev.js` מריץ API + Vite; Vite מפנה `/api/*` ל‑`localhost:4000` |

## התקנה והרצה

דרישה מקדימה: Node.js 20.11+ (נבדק על Node 22).

```bash
cd project
npm install        # פעם ראשונה בלבד
npm start          # מריץ יחד: API על :4000  +  Vite על :5173
```

פותחים בדפדפן: **http://localhost:5173** ומתחברים עם אחד ממשתמשי הדמו.

פקודות נוספות:

| פקודה | פעולה |
|---|---|
| `npm run dev` | Vite בלבד |
| `npm run server` | שרת ה‑API בלבד |
| `npm run build` | בנייה לפרודקשן אל `dist/` |
| `npm run lint` | הרצת oxlint |

## ממשקי ה‑API

כל הנתיבים מתחת ל‑`/api` (Vite מסיר את הקידומת בפיתוח).

| קבוצה | Method + Path | תיאור |
|---|---|---|
| התחברות | `POST /login` · `POST /logout` · `GET /session` | ניהול סשן; מחזיר את המשתמש עם `role` ו‑`settlementId` |
| מבנים | `GET /reports` · `POST /reports` · `GET /reports/:id` | רשימה מסוננת לפי תחום אחריות; יצירה; פרטים (403 מחוץ לתחום) |
| שיקום | `PATCH /reports/:id/status` · `POST /reports/:id/budget-request` | מעבר סטטוס מדורג; פתיחת בקשת תקציב (נאכף לפי תפקיד) |
| הערכות שמאי | `PATCH /reports/:id/assessment` | שמירת הערכת נזק (נאכף לפי תפקיד + תחום) |
| אישורי רשות | `PATCH /reports/:id/authority-approval` | שמירת אישור תשתיות (נאכף לפי תפקיד + תחום) |
| תיק אכלוס | `POST /buildings/:id/return-home-package` · `GET /files/:name` | הפקת המסמך; הגשתו (`?download=1` להורדה) |

| תהליכי יישוב | `GET/POST /settlement-processes` · `PATCH /settlement-processes/:id/complete` · `POST /settlement-processes/:id/log` | ניהול רשומות ההפקה המרוכזת |
| בריאות המערכת | `GET /system-health` | מדדים מחושבים מנתוני המערכת |

## מגבלות ידועות

- **הכל בזיכרון.** אין בסיס נתונים — הפעלה מחדש של השרת מאתחלת את כל הנתונים (מבנים, משתמשים, הערכות, אישורים, לוגים בזיכרון). קבצי `server/generated/` נשארים על הדיסק.
- **"PDF" מופק כ‑HTML מעוצב.** תיק האכלוס הוא מסמך HTML רשמי בעברית RTL, מוכן להדפסה/שמירה כ‑PDF מהדפדפן. הפקת PDF בינארי אמיתי בעברית דורשת הטמעת פונט עברי + ספריית PDF — מחוץ להיקף ה‑MVP.
- **שרת ההודעות מדומה.** אינו שולח מיילים אמיתיים; מדמה הצלחות/כשלים לפי המצב הנבחר וכותב יומן CSV.
- **התחברות מפושטת.** token אקראי ב‑`Map` בזיכרון, ללא JWT/תפוגה/הצפנה — מספיק לזיהוי מי ביצע כל פעולה.
- **אין חבילת בדיקות אוטומטית בקוד.** האיכות נשמרת דרך `npm run lint`, `npm run build`, ואימות ידני מקצה‑לקצה של כל תהליך.
